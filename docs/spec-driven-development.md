# Spec-driven development (SDD) в kokoro-ru-tts

Стандарт описывает, как в этом проекте фиксировать требования до написания
кода: каждая заметная правка поведения начинается со спецификации в `docs/specs/`,
реализуется по ней и проверяется по её критериям приёмки.

Документ — часть репозитория. Меняя процесс, правьте его вместе с кодом.

Если вы впервые сталкиваетесь с подходом, начните с учебника
[spec-driven-development-guide.md](spec-driven-development-guide.md): там
объяснения простыми словами, примеры и разбор типичных ошибок.

Для AI-агентов соблюдение стандарта обязательно: см. раздел «Обязательный
процесс: spec-driven development (SDD)» в `AGENTS.md`.

## 1. Зачем это нужно

- Требование сформулировано до кода, а не восстанавливается по диффу.
- Понятно, **что** считается готовым: у спека есть измеримые критерии приёмки.
- Решения и компромиссы не теряются: спека хранит контекст и отвергнутые
  варианты.
- Тесты привязываются к требованиям, а не появляются «по ходу».
- Агент или новый участник может восстановить замысел без чтения истории чата.

## 2. Когда спека обязательна

Спека нужна, если изменение затрагивает хотя бы одно из:

- поведение CLI (аргументы, режимы, формат вывода, коды возврата);
- пользовательский сценарий (что и куда сохраняется, как обрабатываются ошибки);
- формат или семантику очистки Markdown и разбиения на предложения;
- контракт модулей (`resolve_sources`, `Settings`, `synthesize`, публичные
  функции и структуры данных);
- зависимости и требования к окружению.

Спека **не нужна** для:

- исправления опечаток, комментариев, форматирования;
- чисто внутреннего рефакторинга без изменения поведения (достаточно тестов);
- обновления версий зависимостей без смены контракта;
- правок README/доков, не меняющих смысл поведения.

Сомневаетесь — заводите короткую спеку: это дешевле, чем восстанавливать
замысел потом.

## 3. Структура документов

```
docs/
├── README.md                       # индекс документации
├── spec-driven-development.md      # этот стандарт
└── specs/
    ├── TEMPLATE.md                 # шаблон спека
    ├── 0001-narration-folders.md   # спеки по порядку
    └── 0002-....md
```

Правила:

- Один спек — один файл. Имя: `NNNN-краткое-имя.md`, где `NNNN` — следующий
  свободный номер (0001, 0002, …). Номер не переиспользуется.
- Имя файла — латиница в kebab-case, без дат и версий в названии.
- Версии не плодим: история правок живёт в git. Отменённая спека получает
  статус `Rejected`, заменённая — `Superseded by NNNN`.
- Спеки не удаляются после реализации: это архив решений.
- `TEMPLATE.md` не нумеруется и не считается спекой.

## 4. Жизненный цикл

| Статус | Что значит |
|---|---|
| `Draft` | Черновик, обсуждается, код не пишем |
| `Approved` | Требования согласованы, можно реализовывать |
| `In progress` | Идёт реализация |
| `Implemented` | Код есть, тесты добавлены, критерии приёмки проверены |
| `Rejected` | Отказались; причина указана в спеке |
| `Superseded by NNNN` | Заменён другой спекой; ссылка обязательна |

Порядок работы:

1. **Предложение.** Создайте спеку из `TEMPLATE.md`, заполните контекст,
   поведение и критерии приёмки. Статус `Draft`.
2. **Согласование.** Проверяем: нет ли противоречий с текущим поведением,
   README и `AGENTS.md`; хватает ли критериев, чтобы понять «готово/не готово».
   Статус `Approved`. Для мелких правок допускается сразу `Approved` одним
   человеком — но критерии приёмки всё равно обязательны.
3. **Реализация.** Код и тесты пишутся по спеке. Если по ходу выяснилось, что
   требование неверно, **сначала правится спека**, затем код. Статус
   `In progress`.
4. **Проверка.** Прогоняются тесты и ручные сценарии из спека, заполняется
   раздел «Проверка». Статус `Implemented`.
5. **Поддержка.** Если поведение меняется позже, заводится новая спека или
   ставится `Superseded by`. Старую не переписываем задним числом.

## 5. Обязательные разделы спека

Шаблон: `docs/specs/TEMPLATE.md`. Минимальный набор:

1. **Шапка:** номер, название, статус, дата, связанные файлы/спеки.
2. **Контекст и проблема:** почему это нужно, что не так сейчас.
3. **Цели и не-цели:** что входит в изменение, что осознанно оставляем за
   рамками.
4. **Пользовательский сценарий:** как это выглядит для человека, команды
   запуска, примеры.
5. **Требования:** нумерованные `FR-1`, `FR-2`, … — проверяемые утверждения
   о поведении.
6. **Критерии приёмки:** `AC-1`, `AC-2`, … в формате «дано / когда / тогда»
   или чёткий чеклист. Каждый критерий должен быть проверяем тестом или
   ручным сценарием.
7. **Крайние случаи и ошибки:** пустые папки, отсутствующие пути, битые
   файлы, конфликты имён, кодировки.
8. **Решения и альтернативы:** что выбрали и почему, что отвергли.
9. **Влияние:** какие модули, тесты, README и `AGENTS.md` меняются; есть ли
   обратная совместимость.
10. **Проверка:** какие тесты/команды подтверждают выполнение, дата прогона.
11. **Открытые вопросы:** только для `Draft`/`Approved`; к `Implemented`
    список должен быть пуст или явно перенесён в не-цели.

Не нужно писать «как устроен код построчно»: спека описывает **поведение и
контракты**, а не реализацию. Исключение — если ограничение важно для
поведения (например, лимит ~500 фонем).

## 6. Критерии приёмки: требования к формулировке

Хорошо:

- `AC-1`: «При запуске `main.py <папка> --narration` обрабатываются только
  `.md`/`.markdown` из папок `narration`, включая вложенные; файлы рядом с
  ними не обрабатываются».
- `AC-2`: «Если папки `narration` не найдены, печатается сообщение с путём
  поиска и код возврата 1; синтез не запускается».

Плохо:

- «Работает корректно».
- «Поддерживает вложенные папки» (какие именно? какие файлы? что с ошибками?).
- «Красивый вывод».

Правила:

- Один критерий — одно проверяемое утверждение.
- Указывайте вход (команда, структура папок), ожидаемый результат и код
  возврата, если он важен.
- Формулируйте в терминах наблюдаемого поведения, а не внутренних функций.
- Критерии не переписываются после реализации, кроме фактических ошибок
  в формулировке; изменение требования — это новая спека.

## 7. Связь с кодом и тестами

- В спеке есть раздел «Проверка»: соответствие `AC-N` → тест или ручная
  команда. Например, `AC-2 → tests/test_batch.py::test_narration_without_dirs_reports_error`.
- Если критерий нельзя проверить автоматически, опишите ручной сценарий и
  отметьте, почему автоматизация нецелесообразна (например, нужен реальный
  синтез и сеть).
- Тест без критерия допустим, но критерий без проверки — нет.
- Имена тестов делайте описательными: они служат ссылками из спека.

## 8. Документация и роли

- **Спек** — источник истины о конкретном изменении и его границах.
- **README** — пользовательская документация: как запускать и что ожидать.
  Обновляется при изменении CLI или сценария.
- **AGENTS.md** — правила для людей и AI-агентов: как менять код, чего не
  делать. Ссылается на стандарт SDD и на актуальные спеки.
- **docs/** — процесс и архив решений.

В небольшом проекте роли совмещены: автор спека он же реализует. Внешнее
ревью желательно для изменений CLI и публичных контрактов, но не обязательно
как отдельный этап.

## 9. Ретроспективные спеки

Иногда функциональность уже есть в коде, а спеки нет: проект развивался до
внедрения SDD или изменение пришло как срочный багфикс. В этом случае
создаётся **ретроспективная спека** — описание уже принятого поведения.

Правила:

- статус сразу `Implemented`, дата — дата коммита или релиза;
- в шапке явно указано «ретроспективная» и перечислены коммиты-источники;
- описывается итоговое поведение, а не ход мыслей задним числом;
- причины решений указываются, только если они видны в коде, сообщении
  коммита или документации; иначе честно пишется «причина в истории не
  зафиксирована»;
- один коммит может дать несколько спек, если в нём несколько независимых
  изменений; несколько коммитов — одну спеку, если они образуют одну фичу;
- нумерация продолжает общий список, а не переписывает историю;
- раздел «Проверка» ссылается на актуальные тесты с пометкой, что они могли
  появиться позже самого изменения;
- ретроспективная спека не оправдывает новое изменение: новое поведение
  оформляется обычной спекой вперёд.

Ретроспективные спеки нужны для онбординга, аудита и чтобы правило «спека —
источник истины» не оставляло дыр в истории.

## 10. Лёгкий режим для небольших изменений

Если изменение небольшое (один флаг, одно сообщение об ошибке, один крайний
случай), спека может быть короткой: контекст в 2–3 предложения, 3–5
требований, 2–4 критерия приёмки, раздел «Проверка». Не раздувайте документ
искусственно, но не пропускайте критерии приёмки.

## 11. Definition of Done

Изменение считается завершённым, когда:

- [ ] спека существует и имеет статус `Implemented`;
- [ ] все `AC-*` выполнены и проверены (тестом или ручным сценарием);
- [ ] `python -m unittest discover -v` зелёный;
- [ ] сценарий `python main.py input/example.md --clean-only` работает;
- [ ] README обновлён, если изменился пользовательский сценарий или CLI;
- [ ] `AGENTS.md` обновлён, если изменились правила работы с кодом;
- [ ] в спеке заполнен раздел «Проверка» с датой и списком тестов;
- [ ] тяжёлые импорты не подняты на уровень модулей, тесты не требуют модели
      и сети.

## 12. Чеклист автора спека

- [ ] Номер следующий свободный, имя файла в kebab-case.
- [ ] Статус соответствует реальности, дата актуальна.
- [ ] Контекст объясняет проблему, а не только решение.
- [ ] Есть не-цели: что изменение сознательно не делает.
- [ ] Требования пронумерованы и проверяемы.
- [ ] У каждого критерия приёмки есть способ проверки.
- [ ] Описаны ошибки и крайние случаи.
- [ ] Указано влияние на README, `AGENTS.md`, тесты.
- [ ] Открытых вопросов нет к моменту `Implemented`.
