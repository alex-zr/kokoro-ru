# AGENTS.md

Инструкции для AI-агентов и разработчиков, работающих с этим репозиторием.

## Что это за проект

CLI-утилита: берёт Markdown-файл, очищает разметку, режет текст на предложения
и озвучивает русской моделью [kokoro-ru](https://huggingface.co/zaakirio/kokoro-ru)
(порт Kokoro-82M, голоса `sveta`, `masha`, `dima`). Результат — `.mp3`
(по умолчанию; промежуточный `.wav` удаляется) или `.wav` с `--no-mp3`.
Очищенный `.txt` создаётся только на время проверки и удаляется после успешной
озвучки; с `--clean-only` он остаётся.

Проект небольшой, без фреймворков и сборки. Весь код — обычный Python-пакет
`kokoro_tts/` + точка входа `main.py`.

## Быстрый старт

```bash
# окружение уже создано в .venv (Python 3.12)
source .venv/bin/activate
pip install -r requirements.txt

# тесты (модель и torch не нужны)
python -m unittest discover -v

# только очистка текста (модель не скачивается)
python main.py input/example.md --clean-only

# полный синтез: голос dima и mp3 по умолчанию
python main.py input/example.md

# другой голос / только wav
python main.py input/example.md --voice masha
python main.py input/example.md --no-mp3

# пакетно: все .md из папки, результаты рядом с исходниками
python main.py input
```

На macOS для синтеза нужны `brew install espeak-ng ffmpeg` (`ffmpeg` нужен для
mp3, который сохраняется по умолчанию). Python 3.10–3.12: пакет `kokoro` может
не поддерживать более новые версии.

## Структура

```
main.py                       # argparse + оркестрация: md -> txt -> wav/mp3
kokoro_tts/
  config.py                   # REPO_ID, SAMPLE_RATE, MAX_PHONEMES, VOICES, Settings
  markdown_cleaner.py         # Markdown -> абзацы чистого текста
  chunking.py                 # абзацы -> предложения -> половины длинных фраз
  synthesizer.py              # загрузка kokoro-ru и синтез в numpy-массив
tests/                        # unittest, без тяжёлых зависимостей
input/example.md              # пример входа
output/                       # опциональная папка для -o (в git не попадает)
docs/                         # SDD: учебник, стандарт, спеки в docs/specs/
model/                        # скачанный репозиторий модели (в git не попадает)
```

Поток данных:

```
.md --clean_markdown--> текст --split_paragraphs/split_sentences--> предложения
    --RuG2P--> IPA --KModel + voice pack--> float32 @ 24 кГц --save_wav--> .wav
```

## Обязательный процесс: spec-driven development (SDD)

Это правило приоритетнее привычки «сначала код». Любое задание, которое
добавляет функциональность или меняет наблюдаемое поведение (CLI, формат
файлов, очистка Markdown, разбиение на предложения, публичные функции,
зависимости), выполняется только через спек.

Порядок для агента:

1. Проверить `docs/specs/`: возможно, спека уже есть. Прочитать её и
   стандарт `docs/spec-driven-development.md` (новичкам — учебник
   `docs/spec-driven-development-guide.md`).
2. Если спеки нет — создать `docs/specs/NNNN-краткое-имя.md` из
   `docs/specs/TEMPLATE.md`, где `NNNN` — следующий свободный номер.
   Статус — `Draft`.
3. Заполнить контекст, цели и не-цели, требования (`FR-*`) и критерии
   приёмки (`AC-*`). Не начинать код, пока нет проверяемых критериев.
4. Перевести спеку в `Approved` (для небольших правок в проекте допускается
   самосогласование) и только затем менять код и тесты.
5. Связать каждый `AC` с тестом или ручной проверкой в разделе «Проверка».
6. Завершить задачу: статус `Implemented`, проверка заполнена,
   `README.md`/`AGENTS.md` обновлены, тесты зелёные.

Если поведение уже есть в коде, а спека отсутствует (наследие до SDD), агент
создаёт **ретроспективную спеку** по разделу 9 стандарта: статус
`Implemented`, пометка «ретроспективная», ссылки на коммиты-источники,
описание итогового поведения без выдуманных задним числом обсуждений.

Запрещено:

- писать код новой фичи до появления спека;
- оправдывать пропуск спека «маленьким изменением» — используйте лёгкий
  режим (контекст, 1–3 требования, 1–3 критерия, раздел «Проверка»);
- менять требование в коде, не поправив спеку;
- ставить `Implemented` без заполненного раздела «Проверка»;
- удалять старые спеки или переписывать их задним числом.

Исключения (спека не нужна): опечатки, комментарии, форматирование, чистый
рефакторинг без изменения поведения, правка документации без смены смысла,
обновление зависимости без изменения контракта. Если сомневаетесь — считайте,
что спека нужна.

Если запрос пользователя противоречит этому правилу, агент всё равно сначала
создаёт спек (или указывает на существующий) и сообщает об этом, а не молча
пишет код.

## Правила изменения кода

- **Тяжёлые импорты — только лениво.** `torch`, `kokoro`, `huggingface_hub`,
  `soundfile` импортируются внутри функций (`synthesizer._load`, `save_wav`,
  `main.main`), чтобы `--clean-only` и тесты работали без них. Не поднимайте их
  на уровень модуля.
- **`markdown_cleaner.py` и `chunking.py` должны оставаться без зависимостей**
  (только стандартная библиотека). Это позволяет тестировать их без модели.
- Комментарии, docstring'и и пользовательские сообщения — **на русском**,
  в стиле существующего кода.
- Настройки и константы — в `kokoro_tts/config.py` (`Settings` — dataclass).
  Не хардкодьте голоса/частоту/лимиты в других модулях.
- Пути считаются от корня проекта (`ROOT` в `main.py`,
  `MODEL_DIR` в `synthesizer.py`), а не от текущей директории.
- Аргумент один: файл или папка. Файл озвучивается один, папка — пакетно
  (все `.md` верхнего уровня). Режим определяется по `source.is_dir()`
  (`resolve_sources`), флаг `--batch` оставлен только для совместимости.
- `--narration [NAME]` включает рекурсивный поиск папок `NAME` (по умолчанию
  `narration`) и сбор `.md`/`.markdown` верхнего уровня из каждой.
  Имя по умолчанию — `NARRATION_DIR_NAME`, служебные папки — `SKIP_DIRS`
  в `config.py`. Путь указывается перед флагом (argparse иначе примет его за
  имя); `narration_looks_like_path` подсказывает про порядок аргументов.
  Без флага поведение папок не меняется.
- Процесс для новой функциональности и изменений поведения — обязательный
  SDD-цикл из раздела «Обязательный процесс: spec-driven development (SDD)»
  выше. Спека — источник истины: меняете требование — сначала правьте спеку,
  затем код.
- В пакетном режиме результаты сохраняются рядом с исходными `.md`
  (через `audio_path_for`), `-o` запрещён, а модель загружается один раз
  на всю пачку. Ошибка в одном файле не должна прерывать остальные. Во время
  синтеза показываются прогресс-бар предложений текущего файла и общий
  прогресс-бар завершённых файлов; в `--clean-only` — только общий бар.
- Без `-o` результат сохраняется рядом с исходником в любом режиме:
  имя то же, расширение `.wav`, после конвертации — `.mp3`. Временный
  `<имя>.txt` удаляется после успешной озвучки (в `--clean-only` остаётся).
- Соблюдайте `from __future__ import annotations` и type hints, как в
  остальных файлах.

## Тесты

```bash
python -m unittest discover -v
```

- Тесты **не должны** скачивать модель, требовать `torch`/`espeak-ng` или сеть.
- Изменение поведения `clean_markdown`, `split_*`, `numbers_to_words`
  сопровождайте тестом в `tests/test_markdown_cleaner.py` или
  `tests/test_chunking.py`.
- Тесты, зависящие от `num2words`, помечайте
  `@unittest.skipUnless(importlib.util.find_spec("num2words"), ...)`.
- Ожидаемый результат очистки — точное сравнение строк: следите за пробелами,
  точками в конце абзацев (`_ensure_end`) и пустыми строками между абзацами.

## Подводные камни

- **Лимит ~500 фонем.** Голосовой пак индексируется длиной IPA-строки
  (`self._pack[len(ipa) - 1]`), поэтому длинные фразы делятся через
  `split_in_half`. Не увеличивайте `MAX_PHONEMES` без понимания ограничения.
- **Модель качается в `model/`, а не в кэш Hugging Face.** В кэше файлы —
  симлинки на `blobs/`, и `ru_g2p.py` не находит рядом `espeak-data`.
  Не меняйте `local_dir` на кэш.
- **Повторные запуски не ходят в сеть.** `RussianSynthesizer._model_ready`
  проверяет наличие чекпоинта, голосового пака, `ru_g2p.py`, `config.json` и
  `espeak-data`; если всё есть, `snapshot_download` не вызывается. При
  `--revision` дополнительно сверяется маркер `.downloaded_revision`.
  Обновить модель можно, удалив `model/` или сменив `--revision`.
- **`ru_g2p.py` из репозитория модели выполняется как обычный код** через
  `sys.path.insert` + `importlib`. Для воспроизводимости фиксируйте
  `--revision <коммит>`.
- `sveta` и `masha` используют один чекпоинт (`kokoro-ru-v2-base.pth`),
  `dima` — отдельный. Список — в `VOICES`.
- Числа переводятся в слова без согласования падежей; даты вида `11.11.2026`
  намеренно не трогаются. Это известное ограничение, а не баг.
- Сокращения («т. е.») могут разрезать предложение при `split_sentences`.
- `sveta`, по описанию автора модели, звучит темнее остальных.

## Чего не делать

- Не коммитить `.venv/`, `model/`, `output/*`, `__pycache__/` (см. `.gitignore`).
- Не добавлять тяжёлые зависимости в `markdown_cleaner.py` / `chunking.py`.
- Не запускать полный синтез в тестах и не требовать его для CI.
- Не переписывать `README.md` под свои изменения без необходимости: он
  описывает пользовательский сценарий и ограничения.

## Чек-лист перед завершением задачи

1. Для новой функциональности или изменения поведения спека создана до
   первой строки кода, доведена до `Implemented`, раздел «Проверка»
   заполнен.
2. `python -m unittest discover -v` — зелёный.
3. `python main.py input/example.md --clean-only` — создаёт
   `input/example.txt` и не падает без модели.
4. Новые константы — в `config.py`; новые тексты/сообщения — на русском.
5. Тяжёлые импорты не подняты на уровень модулей.
